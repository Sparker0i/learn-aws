A six-month build plan · ~10–15 hrs/week

Route & Ship

One compounding system, not a pile of tutorials: a Go gateway that routes between AWS Bedrock and a homelab GPU, fronting a Python RAG service — built across six interleaved phases that touch AWS, AI engineering, and advanced Go/Python at once.

Operating rule

You already know your failure mode is spreading thin across experiments instead of finishing a few. So: one flagship system, evolved for 26 weeks, is the only project on this roadmap. If you get the itch to spin up a new framework or a shiny side-repo mid-phase, write it on a "later" list and keep building the gateway. Every new idea gets evaluated by one question: does this make the existing system better, or is it a new thing to finish? Only the first kind gets built now.

What you're actually building

The same two services grow more capable every phase — they never get thrown away and restarted. This is the shape by the end of Phase 2, once routing and streaming are in place.

Phase 0 Weeks 1–2

Foundations & first deploy

AWSGoPython

Get the AWS account and IAM sane, refresh Go/Python project hygiene, and prove the deploy pipeline exists before the real system does. Nothing clever yet — just plumbing.

AWS

  • Dedicated dev account, IAM Identity Center role (not root), MFA on everything.
  • A Budget + billing alarm at ~$100 and ~$150/mo — alerts, not a hard cap, matching your "spend when justified" comfort zone.
  • AWS CLI v2 configured, boto3 and aws-sdk-go-v2 installed.

Go

  • Idiomatic layout (cmd/, internal/), modules, golangci-lint, go test ./... wired into CI.

Python

  • uv for env/deps, ruff + mypy, src-layout package.

Ships this phase

Two scaffolded repos — gateway (Go) and assistant (Python) — each deployed as a trivial hello-world on AWS (Lambda + API Gateway for the assistant, one Fargate run for the gateway), with GitHub Actions redeploying on push to main.

Resources

  • AWS Skill Builder (free) — "Getting Started as a Builder" track, plus the IAM best-practices guide.
  • Effective Go and the first two chapters of 100 Go Mistakes and How to Avoid Them (Teiva Harsanyi).
Phase 1 Weeks 3–6

Core AWS dev services & RAG v0

AWSAI

Learn the AWS services you'll touch constantly, and get a naive but real retrieval pipeline answering questions end-to-end — on a corpus you actually care about, since you'll build eval questions against it later.

AWS

  • S3 for source docs, Lambda + API Gateway for the assistant, CloudWatch Logs.
  • pgvector on RDS for the vector store — SQL is already home turf for you, so this is the lowest-friction way in versus a new managed vector product.

AI

  • Enable Bedrock model access (Claude + Titan embeddings). Chunk a real corpus, embed it, retrieve top-k, stuff into a prompt, generate an answer.

Go

  • Gateway skeleton: a plain net/http reverse proxy to the RAG endpoint. Typed config struct (no scattered os.Getenv), log/slog for structured logs.

Ships this phase

RAG v0 — a live, working "ask a question about my own docs" endpoint on Lambda + API Gateway, callable through the Go proxy.

Resources

  • Chip Huyen, AI Engineering (O'Reilly) — foundations and RAG chapters.
  • anthropic-cookbook on GitHub — RAG examples you can run against Bedrock's Claude models directly.
  • AWS docs: Lambda developer guide, RDS pgvector, Bedrock Runtime API reference.
Where this crosses tracksA managed AWS compute service (Lambda) is now the runtime for your AI logic — deploying it, not just calling an API from your laptop, is the actual AWS+AI skill hiring managers mean by "productionizing LLM apps."
Phase 2 Weeks 7–10

Advanced Go, streaming, and the homelab comes online

GoAWSAI

This is where Go gets genuinely advanced, and where the RTX 5080 stops being a side experiment and becomes part of the architecture.

Go

  • Goroutines/channels/context cancellation, worker pools, -race as a standing habit.
  • Streaming HTTP responses (SSE/chunked) so tokens stream through the gateway.
  • Table-driven + testcontainers-go tests; multi-stage Dockerfile.

AWS

  • Real ECS Fargate service behind an ALB with health checks; secrets in Secrets Manager, not env vars.
  • Optional stretch: mirror one component on EKS, purely to make your existing K8s knowledge transfer explicit and bloggable.

AI & homelab

  • Ollama on the homelab behind a stable endpoint (Tailscale), reachable from the AWS-deployed gateway.
  • Routing logic: cheap/short queries to local Ollama, complex ones to Bedrock — same code path either way.

Ships this phase

The gateway now streams tokens and routes between two real backends — AWS Bedrock and your home GPU — running as a real ECS service.

Resources

  • 100 Go Mistakes — concurrency chapters; the Go blog's "Advanced Go Concurrency Patterns."
  • Alex Edwards, Let's Go Further — production HTTP service structure in Go.
Where this crosses tracksStreaming spans all three: Go's concurrency primitives carry tokens from an AI backend that's sometimes on AWS and sometimes on your own hardware. The cost/latency contrast between those two paths is a differentiator almost nobody else in an interview pool will have.
Phase 3 Weeks 11–15

Real RAG depth, evals, and infrastructure as code

AIAWS

Move past "it works on my one test question" to something you can defend with numbers, and stop clicking around the console.

AI

  • Chunking experiments (fixed vs. semantic vs. recursive), hybrid search, re-ranking.
  • A first agentic loop: the model decides to search vs. answer directly.
  • An evals harness — a golden 20–30 question set, scored automatically, tracked over time.

AWS

  • Rewrite the entire stack as AWS CDK in Python (doubles as Python practice) — gateway, assistant, vector store, networking, IAM, all reproducible from code.
  • Real CI/CD: tests, image build, IaC deploy on merge to main.

Ships this phase

RAG v1 with a measured eval score, and the entire system defined as code.

Resources

  • AI Engineering (Huyen) — evaluation chapters; ragas or promptfoo docs.
  • Eugene Yan (eugeneyan.com) — applied writing on RAG evaluation specifically.
  • AWS CDK Python docs and workshop.
Phase 4 Weeks 16–20

Observability, reliability, security, cost

AWSGoAI

Make it defensible in an interview as "production-ish," not just "it runs." Almost everything here is intersection work.

AWS

  • CloudWatch dashboards/alarms on latency, error rate, and cost; X-Ray tracing across the whole request path.
  • Bedrock Guardrails or a manual filter against prompt injection — this system takes arbitrary user text.
  • An IAM audit pass, and a real cost breakdown: what routing to the homelab actually saves vs. all-Bedrock.

Go

  • Load test the gateway (k6/vegeta), fix what breaks under concurrency.
  • Add a semantic cache to dedupe near-identical queries — a real concurrency-safe cache design problem.

Ships this phase

Dashboards and traces showing real (even synthetic load-test) traffic end to end, plus a documented before/after cost number.

Resources

  • AWS Well-Architected Framework — Reliability and Cost Optimization pillars.
  • Bedrock Guardrails docs; k6 docs for load testing.
Phase 5 Weeks 21–26

Polish, publish, contribute

AWSGoAI

Convert five months of real engineering into artifacts a hiring manager will actually encounter and read.

Publish

  • 3–4 blog posts: system architecture; the homelab-vs-Bedrock cost/latency showdown with real numbers; Go concurrency lessons; how you built and trust your RAG evals.
  • A short demo GIF/video at the top of the main README.

Contribute

  • One real, small, non-trivial PR to a project you actually used building this — an SDK example, an Ollama tooling repo, ragas, whatever you genuinely touched.

Package

  • A one-page case study: what it does, one architecture diagram, 4–5 metrics that matter (p50/p95 latency, eval score, cost/month, cost saved by local routing).

Final self-interview

Could you whiteboard this system cold and defend every decision — why Fargate and not just Lambda for the gateway, why pgvector and not OpenSearch, why this particular Go concurrency pattern — in a live interview?

Where the tracks actually meet

  • Phase 1AWS + AI — the RAG service's runtime is a managed AWS compute product (Lambda), not a script on your laptop. Deploying it is the skill, not calling the model.
  • Phase 2Go + AWS + AI — token streaming runs through Go's concurrency primitives, across a network hop that sometimes lands on Bedrock and sometimes on your own GPU.
  • Phase 3AWS + AI — infrastructure-as-code makes the AI system reproducible; evals make it measurable. Neither means much without the other.
  • Phase 4All three — observability instruments the Go service, the AI calls, and the AWS infrastructure as one continuous trace, and the cost analysis only exists because you built the homelab routing path in Go.
